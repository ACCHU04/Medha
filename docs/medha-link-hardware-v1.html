1. Safety & prototype disclaimer

MEDHA LINK is being developed as a research/prototype platform, not as a certified medical device. Every claim in this document is scoped to a demonstrator that proves the core idea:

Core demonstrator: real sensor → MEDHA edge device → local processing → offline storage → reconnect → synchronization → hospital dashboard → structured handover.
  • Hardware captures and digitizes signals. Software cleans, validates, stores, synchronizes, visualizes, and performs only clearly bounded prototype analysis.
  • Not for clinical use. No measurement shown is claimed to be clinically valid, and no software output is intended for treatment decisions without qualified human review.
  • Status is explicit. Section 3 separates implemented-and-validated software, implemented-but-hardware-dependent software, and proposed hardware so nothing in this document overstates readiness.

2. System overview architecture

The system is a single end-to-end pipeline: the patient is the source of signal; the edge gateway is the owner of acquisition and offline resilience; the server is the owner of validation, persistence, and coordination; the hospital dashboard is the point of human decision.

4. Hardware architecture — Raspberry Pi 5 gateway

Raspberry Pi 5 (8 GB recommended) is the edge gateway. It is the single computer that runs the device application, the local SQLite database, the offline outbox, the HLC clock, sensor acquisition services, ECG processing, camera capture, the touchscreen UI, the synchronization client, the GPS service, and the Wi-Fi/4G connection manager.

Figure 2 — Hardware block diagram: Pi 5 gateway with ECG AFE, sensor hub, GNSS, 4G, camera, touchscreen, power.

4.1 Why Raspberry Pi 5

  • Compute: quad-core 64-bit CPU with enough margin for acquisition, ECG filtering, camera processing, and the touchscreen UI simultaneously.
  • Interfaces: USB 3, GPIO (SPI/I²C/UART), Wi-Fi + Bluetooth/BLE, CSI camera, DSI display, and PCIe — one board covers every sensor link in this design.
  • Software fit: the existing Python device client (services/sync/device.py) and server stack already target Python 3.x + Linux-style packaging; the Pi 5 runs the same code path used by the browser simulator.
Principle: keep the architecture identical to the proven software path — only the signal source changes (browser simulator → real sensor). The offline outbox, HLC, and sync protocol are reused unchanged.

Each measurement is validated on-device, then emitted as the same vital SyncOp the existing pipeline already consumes — the server, dashboard, and handover code need no changes.

5.3 GPS and 4G

  • GPS: u-blox NEO-M9N (GPS/GLONASS/Galileo/BeiDou) over UART → gps SyncOp → server → ETA + dashboard position.
  • 4G: Quectel EC25-class LTE Cat-4 modem over USB with a SIM. For the first prototype, an evaluation board is used instead of designing RF hardware.

6. Offline-first architecture

This is the core engineering bet of MEDHA LINK and the part of the architecture that is already implemented and validated in software. The physical device mirrors the proven pattern 1:1.

Figure 4 — Offline-first flow: every captured op lands in the SQLite outbox; loss of network only delays delivery, never drops data.
Dead-zone behavior: when the ambulance enters a coverage gap, vitals, GPS, ECG, and events keep writing to the SQLite outbox. On reconnect, the flush loop pushes everything in HLC order; the server validates, dedupes replays, resolves conflicts by LWW, and broadcasts to the hospital via WebSocket.

7. Sync / HLC implementation

Every offline op is one SyncOp. The protocol is deliberately small and is already implemented, tested, and proven in the live journey.

7.1 The SyncOp and the push protocol

{
  "batch": [{
    "op": "upsert", "entity": "vital",
    "id": "<uuid>", "device_id": "<uuid>",
    "hlc": "2026-08-12T10:01:01Z:0001:<device-uuid>",
    "data": { "case_id": "...", "heart_rate": 82, "spo2": 97, ... }
  }]
}
POST /api/v1/sync/push  →  { "applied": [{"id","entity"}], "skipped": [{"id","entity","reason"}] }
  • HLC (hybrid logical clock) — services/sync/hlc.py: combines wall-clock with a monotonic counter and device suffix, giving total ordering even across offline devices. Server-side dedupe uses it to detect replays (reason: "duplicate").
  • Device client — services/sync/device.py: SQLiteLocalStore (durable outbox), AmbulanceDevice.record()/flush(), transient failures bump attempts with exponential backoff; permanent rejections move to a dead-letter queue.
  • Server apply — services/sync/apply.py: ownership check (_device_or_reject), per-entity appliers (vital / gps / ecg / transition), dedupe + last-writer-wins, single commit, then WebSocket broadcast.
Figure 5 — Server-side sync/push processing: authenticate → ownership → per-entity apply → dedupe/LWW → commit → broadcast.

9. Encounter / GPS / ETA

The case lifecycle is a small, explicit state machine. It drives what the ambulance and hospital UIs allow, and it is the same machine the browser simulator already exercises end-to-end.

Figure 7 — Case lifecycle state machine. transport_start auto-assigns the nearest hospital; GPS updates feed the ETA shown in the hospital queue.
  • GPS → ETA: each gps SyncOp updates the latest position; services/eta.py recomputes nearest_hospital and eta_minutes, surfaced in the live queue.
  • Auto-assignment: transport_start with no destination picks the nearest hospital automatically — verified live (destination resolved, ETA populated).

10. Hospital coordination

Coordination is realtime: the moment the server commits a sync batch, the hospital dashboard is updated over WebSocket — no polling for vitals or case events.

11. Handover / FHIR / CDA

At handover, the server assembles the complete episode into two interoperable, standards-shaped exports:

  • FHIR R4 document bundle (GET /api/v1/cases/{id}/handover?format=fhir, application/fhir+json) — a Bundle of type document containing Composition, Patient, Encounter, Practitioner, Location, Observations (vital signs), DiagnosticReport, and ECG entries.
  • CDA R2-style XML (format=cda, text/xml) — a ClinicalDocument with Record scope, Encounter/Transport, Vital signs, and ECG sections.

Both exports carry the explicit boundary statement "not a certified medical record" in the rendered text.

Verified: FHIR bundle structure, 9 vital-sign observations, 1 ECG entry, CDA well-formedness, all four CDA sections, and the boundary text are asserted in the automated suite and passed in the live 26/26 journey.

14. Current limitations + next hardware-validation steps

14.1 Known limitations (current state)

  • No physical sensors exercised yet. Acquisition service drivers for ADS1292R / SpO₂ / BP are defined but not hardware-validated.
  • Browser-dependent UI acceptance. Canvas ECG rendering, visual cards, IndexedDB state, and print layout are verified by manual acceptance, not automation.
  • Device identity fragility (found during validation). Device IDs are random UUIDs stored in browser storage; a server DB reset orphans them and silently rejects sync until storage is cleared. The hardware client must persist the device identity in stable storage and re-register on reset.
  • WS session hygiene (fixed during validation). WebSocket handlers previously left read transactions open for the socket lifetime, blocking maintenance DDL; fixed by rolling back the auth transaction immediately.
  • No clinical claims. Nothing measured or displayed is clinically validated; the prototype is explicitly non-clinical.

14.2 Next hardware-validation steps (proposed, dependency-ordered)

  1. Raspberry Pi 5 bring-up — Linux image, device app package, outbox/sync client running on-device against the existing server (reuse current code as-is).
  2. ECG AFE validation — ADS1292R eval board → SPI → sample stream → quality + waveform rendering on the touchscreen.
  3. GPS validation — NEO-M9N → live gps SyncOps → server ETA from a moving device.
  4. SpO₂ / temperature validation — sensor hub → validated vital SyncOps.
  5. 4G connectivity — EC25 eval board → real-network reconnect flush test in a coverage gap.
  6. Touchscreen UI — port the simulator UI to the Pi display; camera capture for paper ECG.
  7. Power + enclosure — battery/UPS, mounting, cable management; then a full field-drive demo: sensor → device → offline → reconnect → dashboard → handover.
